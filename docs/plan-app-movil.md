# Plan para separar la operación Android, la API y el panel web

## Cómo funciona hoy

Un proceso Express sirve la web, la API y las imágenes de firmas. El almacenista prepara una recepción rápida en `/` o detallada en `/detallada`. En `/registros` consulta el historial y abre Gestionar recepción para devolver o cambiar herramientas. La tablet abre `/firmar` desde un APK que solo aloja un WebView. El servidor guarda los movimientos en SQLite y las firmas en PNG bajo `data/firmas/`. Al crear otro movimiento cancela el que esperaba firma, aunque la interfaz intenta evitarlo con un bloqueo del formulario.

El worktree parte de `main`; la versión que corre en producción queda por confirmar. La referencia indica que el cambio de herramienta ya entró en `main` y que su despliegue estaba pendiente.

## API y panel

Mantener Node.js, Express, better-sqlite3 y los generadores actuales. Un solo proceso en Docker monta el volumen y administra SQLite y los PNG. El mismo proceso sirve el panel y sus API bajo el mismo origen, de modo que el navegador usa su sesión y descarga archivos sin CORS. Android usa HTTPS y JSON. Publicar el contrato para Android antes de implementar pantallas y probarlo con datos sintéticos.

### Contrato HTTP

| Ruta actual | Reutilización y alcance propuesto |
| --- | --- |
| `GET /api/declaraciones` | Reutilizar ruta y respuesta por tipo. Android toma de aquí el valor inicial editable de la detallada. |
| `GET /api/entregas-pendientes` | Reutilizar ruta y respuesta de negocio para Gestionar recepción. Autorizar al operador. |
| `GET /api/historial` | Reutilizar `{ grupos, sueltas }` para el panel. Cada grupo trae `entrega`, `devoluciones`, `pendientes` y `ciclo`. `devoluciones` incluye los cambios, distinguibles por `tipo`. |
| `GET /api/movimientos` | Reutilizar listado plano de consulta para administración si se usa. Por defecto trae hasta 200 movimientos no cancelados, igual que el límite de recepciones agrupadas del historial. |
| `GET /api/entregas/:id/pdf`, `GET /api/export.xlsx` | Reutilizar descargas y formato para administración. Hoy PDF busca entre hasta 1.000 recepciones y Excel limita sus consultas a 1.000. La prueba de volumen debe cubrir ese corte. |
| `GET /api/salud` | Reutilizar para la prueba de dirección y Docker. Hoy devuelve `ok` y `conectados`; el ajuste nuevo comprueba `ok` y verifica el acceso del dispositivo por separado. Exponer como máximo el estado mínimo donde se permita acceso anónimo. |
| `GET /api/activo` | Mantener la lectura inicial. Hoy devuelve el movimiento o `null`. Limitar el contenido por rol y tablet, con `Cache-Control: no-store`. |
| `POST /api/movimientos` | Mantener ruta, cuerpo y respuesta `201`. Cambiar la sustitución automática por `409` si hay un activo. Admitir creación únicamente al operador autorizado. |
| `POST /api/movimientos/:id/firmar` | Mantener ruta y formato de ambas firmas como data URL de PNG. Para la app exigir ambas, validar imagen y tamaño, comprobar que el dispositivo está autorizado y confirmar con `200` solo tras guardar las dos. Hoy la firma del responsable es opcional en la API aunque la tablet solicita ambas. |
| `POST /api/movimientos/:id/cancelar` | Mantener ruta y respuesta `{ ok: true }` para el operador. Cancelar solo el ID esperado y avisar del cambio real de estado. |
| `GET /api/eventos` | Disponible para LAN durante la transición. Si se conserva, autenticarlo, filtrar por rol y usar sus eventos como aviso para volver a consultar. |
| `GET /firmas/:archivo` | Mantener URLs relativas para los PNG históricos. Servirlos solo a administración con acceso al registro. |

En el alta de recepción se envían `tipo: ENTREGA`, `modo: rapida` o `detallada`, empleado, cédula, departamento, responsable, lista de herramientas con descripción, cantidad y estado, y observaciones generales. La detallada admite `codigoEmpleado`, observaciones de línea y `declaracion`. El servidor asigna códigos `TRX` y `TRXD` y normaliza el texto por defecto. La interfaz dice «recepción» y el contrato conserva `ENTREGA`.

Una `DEVOLUCION` envía `entregaId` y las líneas pendientes seleccionadas por ID con condición de regreso y observaciones. Un `CAMBIO` envía también `sentido` por línea, con IDs pendientes para `devuelve` y descripción, cantidad, condición y observaciones propias para `recibe`. El servidor hereda los datos del empleado y el modo. Valida pertenencia, pendientes y líneas repetidas. Asigna a cada herramienta nueva un ID mayor que los del grupo, incluidos los cambios cancelados. `cuentaDe()` calcula el universo y los cierres con movimientos firmados. El campo derivado `devuelta` en historial se conserva como salida calculada. La unidad de devolución sigue siendo la línea completa.

Añadir una lectura de estado por ID, `GET /api/movimientos/:id/estado`, restringida al operador y a la tablet autorizada para ese movimiento. Devuelve `id`, `codigo`, `estado` y `firmado_en`. Permite resolver un envío con respuesta perdida aunque `/api/activo` ya devuelva `null` o un ID distinto. Definir errores JSON con código estable y mensaje en español para `400` (validación), `401` (sesión), `403` (permiso), `404` (ID desconocido en el alcance autorizado) y `409` (conflicto de estado). En el piloto conservar los errores que espera el cliente web anterior mediante la configuración de transición.

En la primera salida, consultar el activo tras un alta con resultado incierto, mostrarlo al operador y exigir confirmación antes de otra alta. Si el activo desapareció, consultar el historial reciente y verificar el resultado con la tablet antes de repetir. Los reintentos automáticos de creación quedan para una ampliación aprobada con una tabla de idempotencia en la misma base. La tabla permitiría guardar clave, huella del contenido e ID en la misma transacción del alta y devolver el movimiento original incluso tras reiniciar. Firmar y cancelar se reconcilian por ID. Preparar los PNG en temporales y publicar las referencias junto al cambio de estado tras comprobar ambos archivos. Probar limpieza de temporales y huérfanos tras fallos y excluir archivos referenciados por movimientos firmados.

### Acceso y conectividad

- Panel con cuentas administrativas identificadas mediante Cloudflare Access con identidad corporativa. Validar su identidad en el origen y aplicar autorización en Express antes de servir HTML, API, exportaciones e imágenes. Usar sesión segura de navegador y evitar caché de datos personales.
- Android con alta por dispositivo mediante código de un solo uso y una credencial revocable guardada con protección de Android Keystore. Añadir `POST /api/dispositivos/vincular` y una lectura autenticada para probar la sesión. El operador se identifica individualmente mediante el proveedor corporativo y recibe su propio permiso. La tablet de firma solo lee y firma el movimiento asignado. Guardar la configuración de dispositivos fuera del esquema de movimientos, en almacenamiento persistente administrado por la API. Registrar acciones y revocaciones con identificadores, sin volcar cédulas, credenciales ni firmas en logs.
- Usar un túnel con nombre y hostname estable. Publicar el panel con su política de Access y configurar el hostname móvil para autenticar en la API por dispositivo y rol, con rutas explícitas y límites de intentos. Si se exige Access también para Android, evaluar credenciales de servicio provisionadas por dispositivo y rotables, junto con el permiso de la API. Limitar el acceso directo al origen y aplicar las mismas autorizaciones al acceso por LAN. El código compartido de la web actual solo se conserva para la vuelta atrás bajo el perímetro autorizado. [Cloudflare Tunnel y enrutamiento](https://developers.cloudflare.com/tunnel/concepts/routing/) · [Cloudflare Access para aplicaciones publicadas](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/).
- Por el túnel, iniciar sondeo HTTPS de `/api/activo` al abrir o despertar la app y cada 3 s en primer plano. Usar una petición en vuelo, tiempos límite, espera progresiva ante fallo y consulta inmediata al recuperar conexión. Deduplicar por ID y reconciliar la operación anterior por su estado. Para el panel, refrescar historial al volver a la pestaña y periódicamente mientras la lista esté visible. Verificar en el túnel que aparece un nuevo activo dentro de un intervalo de sondeo más la latencia de red. El servidor actual emite SSE con latidos cada 8 s y el cliente web activa sondeo al quedarse sin señales durante unos 14 s. El túnel retuvo ese flujo en las pruebas del proyecto; no usar SSE como requisito para operar.

## Aplicación Android y tablet

- Kotlin y Jetpack Compose para interfaz nativa, con cliente HTTP y estado de pantalla ligado a su ciclo de vida. Android es la plataforma solicitada y esta opción integra dibujo táctil, pantallas adaptables, almacenamiento protegido y quiosco sin una segunda plataforma. Fijar versión mínima tras inventariar equipos. El APK de referencia usa `minSdk 26` y sirve para documentar el comportamiento esperado.
- Perfil **Almacén** con Recepción rápida por entrega diaria, Recepción detallada por herramienta asignada y Gestionar recepción. La rápida crea recepciones con los campos habituales. La detallada incorpora ficha, observaciones por herramienta, declaración editable y el catálogo del formulario, con Mantenimiento. Gestionar parte de recepciones firmadas pendientes y muestra su detalle. Permite devolución parcial por líneas o cambio con entradas y salidas, además de consultar el estado de la firma y cancelar expresamente. Mantener el borrador ante un conflicto y bloquear el envío mientras ocupe el turno un activo.
- Perfil **Firma** con espera, resumen de herramientas y declaración, firma del empleado, firma del almacenista y confirmación. La pantalla de firma y su espera carecen de campos de texto y teclado. Los botones permiten borrar y confirmar en cada paso. Dibujar con coordenadas del lienzo, suavizar el trazo y exportar PNG transparente recortado a la tinta, manteniendo el lienzo de trabajo. Conservar los dos pasos en memoria ante rotación, despertar, reconexión y avisos del mismo ID. Mostrar fallos dentro de la pantalla. Si muere el proceso antes de confirmar, consultar el servidor, indicar lo ocurrido y volver a capturar las firmas si sigue pendiente.
- Tablet dedicada con modo Lock Task mediante un controlador de políticas que autorice el APK. En un equipo sin gestión, usar fijación de pantalla para la prueba manual. Reservar la salida del quiosco y los ajustes para soporte autenticado. Provisionar la URL HTTPS mediante configuración administrada o QR, con opción de edición en ajustes protegidos fuera del perfil de firma. El gesto de tres dedos durante tres segundos puede abrir esa entrada de soporte, sin consumir el trazo. Probar URL y sesión antes de guardar, conservar la anterior al cancelar y pedir vinculación de nuevo al cambiar de origen. [Modo Lock Task en Android](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode).

### Una tablet o varias

Recomendar un equipo de almacén y una tablet de firma dedicada para el piloto. Con una sola tablet física se alterna entre Almacén autenticado y Firma bloqueada, y el retorno al formulario exige desbloqueo del operador. Con varias tablets conservar **un solo movimiento en espera en todo el sistema** y seleccionar explícitamente una tablet de firma. La asignación se valida en el servidor con la credencial del dispositivo. Las demás reciben estado de espera sin datos del empleado.

Comprobar disponibilidad, preparar el movimiento y asignar su código dentro de la misma transacción de escritura. Con dos creaciones simultáneas, solo una obtiene `201`; la otra conserva el borrador y recibe `409`. Cancelar libera el turno y cualquier firma tardía queda rechazada. Para el despliegue con una tablet basta una vinculación persistente. Habilitar selección de varias únicamente con asignación durable comprobada tras reinicio. Si se aprueba habilitar varias, proponer una tabla de asignación con ID del movimiento e ID de tablet, escrita en la misma transacción. La ampliación evita perder o cruzar la asignación entre una creación y un reinicio. Si la tablet asignada se pierde, el operador cancela explícitamente y recrea en otra. El paralelismo de firmas por sede o tablet cambiaría la regla global y requiere otra decisión del dueño.

## Panel administrativo y comprobantes

Mantener `/registros` con las dos pestañas, sus conteos, detalle, firmas y sus estados calculados. Preservar la pestaña al volver del detalle y mostrar las devoluciones antiguas sueltas en la rápida. Excel va en la lista y PDF en el detalle de la recepción. Proponer búsqueda por código y filtros de fecha o empleado como mejora posterior. Convertir `/` en entrada a registros y retirar `/detallada`, `/firmar` y Gestionar recepción del panel al cortar a Android. Durante el piloto probar la edición móvil sobre una copia aislada y mantener el cliente anterior para contingencia. La retirada incluye verificar acceso directo a archivos HTML y las autorizaciones de API.

- Excel conserva Registro de Firmas e Informe Diario. El informe toma el universo de `historial()` y emite valores por herramienta de recepciones firmadas, con el cierre ya calculado. Mantener las imágenes protegidas en la hoja de firmas con `objects: false`, `twoCell`, desplazamientos EMU nativos y columna localizada por clave. Informe Diario sigue sin protección. Comparar el contenido generado con casos de cambios, devoluciones y firmas históricas.
- PDF conserva el grupo y las firmas, con coordenadas explícitas, marca dibujada y margen inferior temporal a cero para el pie. Probar recepciones largas, el par de firmas y la ausencia de folios vacíos. Conservar la exclusión de `modo` del PDF y del Excel. Los formularios Excel originales de la raíz siguen disponibles.

## Docker, datos y recuperación

Mantener el servicio `firmas` con API y panel estático en el puerto interno 3000 y el montaje actual `./data:/datos`. Agregar o conservar `tunel` como servicio de entrada en la red de Compose. Conservar el 8090 del host cuando haga falta para LAN, con acceso restringido y HTTPS para los clientes operativos. Mantener `America/Bogota` para la serie anual y los comprobantes. Fijar y archivar las versiones de imágenes y APK de cada corte. Guardar secretos de despliegue fuera del repositorio y del APK.

La primera salida mantiene el esquema de `movimientos` y los PNG originales. No se agrega una columna `devuelta`. Preservar IDs, códigos, fechas, modos, declaración personalizada, enlaces y nombres de archivos. Mantener las migraciones de arranque ya existentes para bases antiguas, incluidos el valor por defecto `rapida`, el relleno de IDs que faltan y los índices después de `ALTER TABLE`. Revisar los efectos de arranque con una copia aislada antes de actualizar. Cualquier ampliación posterior para idempotencia o asignación requiere aprobación, pruebas en copia y una receta de lectura con la versión anterior.

Respaldar **todo** `data/`, incluida la base, sus archivos auxiliares presentes, las firmas y la configuración persistente que se aloje allí. Hacer la copia con el escritor detenido para que SQLite en WAL y los PNG representen el mismo punto. Cifrar el respaldo, conservarlo fuera del host con permisos restringidos y ensayar la restauración en una carpeta y servicio aislados. Verificar integridad SQLite, conteos por estado, correspondencia fila a PNG, permisos del usuario del contenedor y comprobantes de muestra. Acordar frecuencia, retención y responsables.

## Despliegue y vuelta atrás

1. Confirmar la versión real de producción, ubicación del volumen, versión y gestión de las tablets y responsable de cada credencial. Archivar imagen, configuración y APK anteriores. Preparar una copia autorizada y protegida del volumen para ensayar migración y restauración, usando datos sintéticos para el resto de las pruebas.
2. Probar en un entorno aislado la API y panel, el túnel fijo, el APK en un equipo real y el modo quiosco. Ensayar recepción rápida y detallada, devolución parcial, cambio, herramienta incorporada que vuelve, cancelación, doble envío, pérdida de conexión durante la firma y recuperación. Comparar Excel y PDF con el entorno anterior y verificar una restauración.
3. Acordar ventana de corte, dejar el turno activo resuelto y detener el escritor. Hacer un respaldo consistente, arrancar una sola instancia nueva sobre el volumen y verificar salud, autenticación, histórico y acceso a firmas. Habilitar el APK y la tablet piloto y observar el primer ciclo completo autorizado antes de retirar las rutas operativas web.
4. Volver atrás si falla el acceso, la recepción y la firma por túnel, la integridad o los comprobantes. Congelar altas, resolver o cancelar el activo, y respaldar el volumen **posterior** al corte antes de detener la versión nueva. Volver a la imagen y al APK anteriores sobre el volumen actualizado solo si el ensayo confirma compatibilidad, incluido CAMBIO. Si la versión desplegada antes del corte no entiende CAMBIO, preparar como contingencia una imagen web anterior compatible con esa semántica antes del piloto. Restaurar el respaldo anterior en un volumen separado si hay corrupción o incompatibilidad. Conciliar los registros y PNG válidos posteriores al corte desde la copia conservada antes de volver a abrir la operación. Usar un identificador de paquete independiente en el piloto para mantener instalable el APK anterior.

## Riesgos y preguntas abiertas

- **Equipos y ergonomía.** ¿Qué modelos y versiones de Android hay, y se usará una tablet compartida o un equipo de almacén con tablet de firma dedicada? ¿Hay gestión de dispositivos disponible para el quiosco?
- **Turno global.** ¿Cuántas tablets y puestos habrá? ¿Se aprueba rechazar nuevas altas mientras exista un activo y exigir cancelación explícita para reasignarlo?
- **Identidad y red.** ¿Hay dominio, túnel fijo y proveedor de identidad corporativo? ¿Quién administra altas, revocaciones y salida del quiosco? ¿La operación debe seguir con el túnel caído mediante HTTPS en LAN?
- **Datos y continuidad.** ¿Qué versión corre en producción, incluye CAMBIO y quién custodia la copia autorizada y los respaldos? ¿Cuánto tiempo de interrupción y pérdida de datos son aceptables y cuál será la retención?
- **Distribución Android.** ¿Quién controla la distribución y custodia el material de firma del APK? ¿El despliegue final debe actualizar el paquete anterior en sitio o puede usar un paquete independiente?
- **Alcance administrativo.** ¿Qué búsquedas necesita el panel, qué volumen exige exportar y qué papel conservan los formularios Excel originales? ¿Se requiere devolver cantidades parciales dentro de una misma línea? El piloto mantiene la devolución por línea completa.
